1. 引言与规范用语

.muapack 是 Union Link 面向 Minecraft 启动器的带签名的客户端发布包。每个包明确表示一个完整目标发布，或从一个明确基准发布到目标发布的更新。发布内容、客户端身份与服务器绑定相互独立。

两种格式的职责
项目v1v2
本地配置、资源与模组包内文件字节包内 overrides/ 下的本地文件字节
mrpack 远程文件Worker 下载、校验并打包只携带下载声明；启动器下载与校验
Minecraft、Java 与加载器Worker 准备精确环境，按平台打包声明要求；启动器解析、缓存与安装
完整包与更新包支持支持
审核、签名和发布同一发布体系；已发布内容不可原地编辑

1.1 规范词汇

必须和不得表示符合协议的必要条件；应当表示除非存在明确理由，否则应遵循的建议；可以表示可选行为。协议字段、枚举和路径均区分大小写，除非明确说明。字段名、枚举值、路径及代码示例保留协议原文。

实现边界：下文对启动器的要求是安装器的实现契约，不表示当前启动器已完成安装、更新恢复、可选文件选择或真实游戏启动验收。

1.2 术语

启动器
面向玩家的 Minecraft 客户端安装与启动程序；本文规定其应实现的行为，实际完成范围见第 12 节。
Worker
后台独立执行导入、校验和组包任务的进程。
完整包与更新包
完整包的 packageType 为 full；更新包为 update，固定基准发布与目标发布。更新包可用与否取决于实际基准，而非版本标签相邻。
发布
不可变的客户端版本事实，由 releaseId 标识；版本标签不是内容摘要。
目标清单
目标发布的完整文件及环境描述，完整包与更新包均必须携带。
基准清单
更新包对应的完整旧发布描述，以身份及精确字节摘要绑定。
载荷
本包实际携带的文件原始字节；不包含仅声明的 v2 远程文件。
内容寻址存储（CAS）
后台按已校验 SHA-256 复用相同文件字节。去重不合并客户端身份、权限或发布历史。

2. 基础类型、身份与平台

2.1 基础类型

类型表示与约束
整数JSON 安全整数；无浮点数。大小为非负字节数。MiB = 220 字节，GiB = 230 字节。
布尔值／空值JSON true、false、null；允许为空的必需字段也不得省略；空值须明确写为 null。
文本（Text）有效 Unicode 字符串；通用身份文本 1–200 个 UTF-16 代码单元，不含 U+0000–001F 或 U+007F。
UUIDorganizationId、releaseId 和 clientId 均为 UUID 字符串。
SHA-256 / SHA-1 / SHA-512分别为 64／40／128 个小写十六进制字符。摘要针对原始文件字节，不针对压缩字节。
路径（Path）1–1000 个 UTF-16 代码单元的 NFC 安全相对路径，分隔符为 /，规则见第 3 节。
签名64 字节 Ed25519 签名的规范 Base64，88 字符并以 == 结尾。

windows-amd64

六平台枚举用于 v1。v2 protocolRevision:2 不声明发布平台集合，环境由启动器按本机操作系统和架构解析。

v1 默认选择除 linux-aarch64 外的五个平台。后台禁用新增 Linux ARM 选择，已有草稿仍可取消该选项；协议保留六个平台标识。v2 不选择架构，不声明平台集合；universal 仅为后台任务标识，不写入分发清单。运行环境是否兼容，由启动器判断。

3. 公共编码与容器

3.1 确定 JSON 编码

  1. 协议 JSON 必须为 UTF-8，无 BOM、缩进、多余空白或结尾换行。
  2. 对象键必须按 JavaScript 字符串比较的 UTF-16 代码单元顺序排序，包括数字形式的键；数组顺序保持不变。
  3. 字符串、整数、布尔与 null 采用 JSON.stringify 标量编码；对象以 :、, 连接，不加空白。不得含未配对代理项、非安全整数、重复键或未知契约字段。
  4. 每份 JSON 最大 16 MiB，根节点深度为 0，递归深度不得超过 32。读取器必须用精确原始字节验证摘要与签名；不能格式化后再验签。

确定编码示例

{"a":[true,null],"b":2}

该示例的最后一个字节是 }，不是换行。此编码是 MUA 契约，不等同于其他 JSON 规范化标准。HTML 中便于阅读的缩进示例不是签名原始字节。

3.2 ZIP 与路径

容器必须为 ZIP／ZIP64，仅使用不压缩（Store，0）或 Deflate 压缩（8）。不得使用加密、符号链接、显式目录条目、重复条目或未声明的附加文件。目录由文件路径隐含表示。必须核对解压大小、CRC-32 和内容摘要；CRC 不代替密码学摘要。

路径必须已是 NFC 相对路径，不以 / 开始，不含反斜杠、空段、. 或 ..。路径段不得含控制字符或 < > : " | ? *，不得以点／空格结尾，不得使用 CON、PRN、AUX、NUL、COM1–9、LPT1–9（包括扩展名形式）。清单必须拒绝大小写冲突与文件／目录冲突。所有实际写入还必须验证解析后的目标位于指定根目录内。

资源上限
项上限
目标文件数100000；v2 至少 1 项
单文件原始大小2 GiB
目标清单文件大小总和40 GiB；v2 包括本地与远程声明，不包括启动器环境
每份 JSON16 MiB；深度 32
ZIP 条目数v1 ≤ 100007；v2 ≤ 100005
ZIP 条目展开大小总和v1 ≤ 40 GiB + 7 × 16 MiB；v2 ≤ 40 GiB + 5 × 16 MiB
异常压缩比展开大小 ≥ 1 MiB 时，不得超过 max(1, compressedSize) × 1000

4. muapack v1

v1 是带完整预安装文件与精确运行环境的单平台容器。包内内容以 SHA-256 对象存储；安装位置由目标平台清单决定，不由对象 ZIP 路径决定。

4.1 容器布局

client-1.4.3-windows-amd64.muapack
├── mua-pack.json
├── metadata/target-manifest.json
├── metadata/base-manifest.json             [仅更新包]
├── metadata/signature.json
├── metadata/environments/<sha256>.json     [目标环境]
└── objects/sha256/<sha256>                 [原始文件字节]

必须携带目标引用的全部环境清单，不要求携带旧基准的环境清单。每个载荷摘要仅对应一个对象条目；同字节文件可复用同一对象。未声明图标、许可证或变更说明不得作为额外 ZIP 文件添加；需要分发时，应纳入目标清单文件或已定义字段。

4.2 mua-pack.json

必需字段类型及规则
format / formatVersion"muapack" / 1
packageType"full" | "update"
platform规范平台值
target / baseReleaseRef / ReleaseRef | null；full 的 base 必须 null
changes{added, modified, removed, policyChanged}；均为数组
payload[{sha256, size}]；摘要唯一，按摘要排序
removalPolicy"retain" | "backup-managed"；必须明确指定

文件身份键为 root + "/" + path。账号文件 launcher_accounts.json、launcher_profiles.json 与实例 .mua 状态不得分发。Java 可执行入口和所有 classpath 条目必须对应 managed 文件；所有 Java 文件必须属于锁定环境，Java 可执行入口与 classpath 文件还必须是非可选文件。不得直接将 UUID 或其他身份文本拼接成本地路径。

4.4 环境清单

每个环境文档必须包含 {format:"mua-environment-manifest", formatVersion:1, kind, platform, resolverVersion, files}。resolverVersion 为文本（Text），files 非空、均为 managed 且非 optional。minecraft／loader 文件使用 instance root，java 文件使用 java root。

kind额外必需字段
minecraftminecraft（精确版本）、sourceMetadataSha256
loaderminecraft、loader:{type,version}、sourceMetadataSha256
javajava:{major,vendor,version,build,executable,archiveSha256,imageType}；可执行入口必须存在且 executable=true

环境内容身份为整份确定编码环境清单的 SHA-256；平台、精确版本、来源元数据／归档摘要、resolverVersion 与显式 imageType 均参与身份。镜像偏好不改变内容身份。目标环境引用、精确版本和每个环境文件必须匹配。当前 v1 清单必须明确记录 imageType，不接受省略该字段的旧结构。默认选择 JRE，JDK 仅由超管选择；缺少 JRE 时明确失败。

5. muapack v2

v2 是基于 mrpack 的签名下载配方容器。Union Link 保存本地模组、配置和资源的 overrides 字节，以及完整发布与更新信息；启动器按声明下载远程文件，并解析、安装运行环境。

当前 v2 的 mua-pack.json、目标清单及更新包基准清单必须包含 protocolRevision:2。不接受省略修订号的旧结构、supportedPlatforms、platformsChanged 或未知修订。包元数据中的修订号直接参与签名，清单中的修订号通过清单摘要绑定；签名域与算法见第 8 节。

5.1 容器布局

client-1.4.3.muapack
├── mua-pack.json
├── modrinth.index.json
├── metadata/target-manifest.json
├── metadata/base-manifest.json             [仅更新包]
├── metadata/signature.json
└── overrides/<path>                       [本地载荷]

当前输入支持标准 mrpack 与已验证的 PCL 内包封装。普通 .minecraft ZIP 不能通过猜测远程地址成为 v2。上传前显式选择分发格式；输入格式不决定输出版本。归一化按远程声明→overrides→client-overrides 叠加，本地覆盖同路径远程文件并继承 optional；server-overrides 与标记为 client:unsupported 的文件不进入客户端。

indexSha256modrinth.index.json 精确字节 SHA-256

removalPolicy"retain" | "backup-managed"；必须明确指定

所有 v2 文件必须位于实例根目录；不得覆盖 versions/、libraries/、assets/、natives/、runtime/、.mua/、.launcher/、.hmcl/ 或 PCL/（含同名根文件），以及 launcher_accounts.json、launcher_profiles.json、accounts.json、usercache.json、usernamecache.json。导入器可以过滤已识别的启动器私有输入，不能放宽分发路径保护。

远程地址必须为持久公开 HTTPS URL，无账号凭据、片段、非 443 显式端口或临时签名令牌；不得含 signature、token、credential、expires、x-amz-、x-goog- 等查询参数，不得指向私有地址或本地域名。启动器下载后必须验证全部声明哈希及大小，以 SHA-512 为主要远程内容身份，不得仅凭 SHA-1 复用。

同一本地 SHA-256 或远程 SHA-512 的大小声明必须一致。未经实际字节校验不得断言本地／远程哈希表示同一内容；启动器可在校验后建立 SHA-512→SHA-256 缓存映射。mods/**/*.jar 模组信息由文件清单派生，未知名称／版本为 null；v2 清单不另设可独立编辑的 mods 数组。

5.4 Modrinth 索引

modrinth.index.json 必须从完整目标清单派生，并与确定编码的预期字节一致。即使是更新包，也必须列出全部目标远程文件，不得只列变化项。本地文件不伪造下载 URL。

索引字段映射
formatVersion / game1 / "minecraft"
versionId / name / summaryrelease.version / release.name / release.summary
dependencies.minecraftruntime.minecraft
加载器依赖键fabric→fabric-loader；quilt→quilt-loader；forge→forge；neoforge→neoforge；值为精确版本，不使用加载器时省略
files只包含 source.type 为 remote 的远程文件，按 path 排序
索引文件项{path, hashes, fileSize:size, downloads:source.downloads, env:{client:optional?"optional":"required", server:"unsupported"}}

Java 要求和启动配置只在 MUA 清单中表达，不写入 mrpack 的 dependencies。本地 optional 由 MUA 清单标记，普通 mrpack overrides 无法表达此能力。完整包可导出普通 mrpack 内容，但普通安装器不提供 MUA 验签、文件策略与更新保证；更新包的 overrides 不完整，不得当作普通完整 mrpack 安装。

5.5 环境解析与锁定

{
  "java": { "imageType": "jre", "major": 21, "vendor": "adoptium" },
  "loader": { "type": "fabric", "version": "0.16.10" },
  "minecraft": "1.21.1",
  "resolverVersion": "mua-runtime-resolver-1"
}

上例为 runtime 子对象的可读示例，不是可独立安装的清单。Minecraft 与加载器版本必须精确，loader 可为 null。java.major 为 7–25 的整数，vendor 固定 adoptium，imageType 为 jre／jdk；默认 JRE，后台 JDK 选项仅超管可选。缺少 JRE 不得静默改用 JDK。

resolverVersion 固定为 mua-runtime-resolver-1；未知规则版本必须拒绝。启动器首次安装选择满足要求的 Java 精确构建，校验可信上游元数据和文件，并在 .mua/runtime-lock.json 记录平台、解析器版本、vendor、imageType、Java 构建版本与归档摘要、Minecraft 与加载器元数据摘要及最终环境清单。该文件由启动器维护，不是包载荷；该文件的格式与持久化机制仍待启动器实现。

后续启动必须复用已校验的锁定环境，不随上游最新版本自动替换；升级／修复须明确重新解析并记录。两台机器首次安装时间不同可能选择不同 Java 安全构建，v2 不承诺 v1 式运行环境逐字节一致。Forge／NeoForge 需要启动器自身具备安装器与受信处理器能力；Worker 对 v1 的支持不能替代启动器实现。

7. 完整包、更新包与安装要求

7.1 基准关系

完整包（full）的 base 必须为 null，文件变化数组必须为空；v2 的 runtimeChanged 和 launchChanged 也必须为 null，v1 不包含这两个字段。更新包（update）必须携带基准与目标清单的完整原始字节。两份清单必须属于同一组织、同一客户端，releaseId 和版本标签不同，且包格式相同。v1 的平台必须相同；v2 的基准与目标均须使用 protocolRevision:2，不检查平台集合。

差异必须从完整清单重新计算。后台针对上传时固定的已发布基准生成更新包，不自动组合历史更新链，也不把未发布草稿对比用作玩家更新基准。没有已发布基准、包格式不同，或 v1 在对应平台没有基准时，只生成完整包。已选定基准损坏时构建必须失败，不能忽略错误继续生成更新包。内容变化必须创建新版本。

7.2 变化清单

字段v1v2
added / removed新增／移除的完整文件描述
modified{before,after}；SHA-256、大小或 executable 改变{before,after}；source 类型、完整 hashes、大小或 executable 改变
policyChanged{before,after}；policy 或 optional 改变，可与 modified 重叠
sourceChanged无此字段{before,after}；前后均为远程文件，内容未修改但 downloads 数组改变
runtimeChanged / launchChanged无此字段；目标仍绑定环境与启动信息null | {before,after}；当前 v2 不允许 platformsChanged

v1 文件键为 root/path，变化列表按此键排序；v2 文件键为 path，变化列表按 path 排序。每一类内不得重复；before／after 的键必须相同。重命名表达为 removed+added，不猜测名称相近的文件是同一个文件。来源 URL 变化仍改变签名发布内容，但本身不代表需要重下载已校验的相同字节。

7.3 载荷选择

包v1v2
full全部目标文件的唯一 SHA-256 对象全部目标本地文件，包含可选文件
updateadded、modified.after、policyChanged.after 的目标对象，按摘要去重同三类中的本地目标文件，按路径去重；远程文件不作为包内载荷

变化后的 preserve 初始字节仍可包含在载荷中，以便目标文件不存在时初始化。v2 包内相同字节可在多个 overrides 路径重复保存，后台仍可 CAS 去重。零载荷更新合法；只有版本或声明变化时，更新包仍携带元数据、清单及签名，大小不保证小于 full。ZIP 大小、实际新 CAS 数据和玩家预计下载量是不同指标。

7.4 文件策略与可选文件

managed
文件缺失或哈希不符时必须安装目标字节；可以复用经过目标哈希校验的缓存。
preserve
不存在时创建；已存在时不得覆盖，也不得因 removed 自动删除。
可选文件（optional）
完整包包含全部本地可选文件；v1 也包含已下载的远程可选文件，v2 保留其远程声明。启动器按 clientId+path 记忆选择，同路径更新沿用，重命名重新确认。关闭的本地 JAR 应保存在缓存／实例外，不留在游戏扫描的 mods 目录；选择不改变发布清单。

7.5 安装、修复与删除

  1. 验证可信签名、清单关系和全部载荷；核对 v1 平台、真实本地基准 releaseId 及清单摘要。v2 环境由启动器解析。
  2. 准备目标文件与环境；未变化文件也必须校验存在与内容。缺失的 v2 远程文件按目标声明下载；缺失且更新包未携带的 v2 本地文件从同目标摘要的 full 修复；v1 复用已校验对象或从目标完整包修复。
  3. 新 Java 环境应形成完整的新摘要目录，可复用旧环境相同字节，不得原地修改其他客户端共享的旧环境。
  4. 成功后原子提交 releaseId、目标清单摘要、平台、文件记录及 v2 环境锁定；失败保留上一安装状态。事务与崩溃恢复须由启动器实现。

retain 只记录移除，不自动清理旧文件；当前后台组包使用 retain。协议也允许 backup-managed：仅对基准明确管理的 instance 文件先备份后移出启用目录，不删除 preserve、玩家自建文件或共享环境。文件被玩家改动时不得假装已保存原字节，应保留冲突与备份记录。启动器的文件移除功能仍待实现。

基准不符时回退 full；full 安装仍须遵循 preserve／optional，可逐文件复用缓存，不表示无条件覆盖目录。远程源失效且无有效缓存时必须失败。预计玩家下载量包括实际需要的包／远程／环境流量；环境未知时显示待解析，不以 CAS 复用率代替玩家节省率。

8. 摘要、签名与信任

8.1 签名文档

metadata/signature.json
字段规则
format"mua-pack-signature"
formatVersion1 或 2，必须匹配包格式
algorithm"Ed25519"
keyId受信公钥 SPKI DER 的 SHA-256 前 24 个小写十六进制字符
metadataSha256mua-pack.json 精确字节的 SHA-256
signature规范 Base64 Ed25519 签名
v1 签名消息 = ASCII("MUA-MUAPACK-V1") || 0x00 || bytes(mua-pack.json)
v2 签名消息 = ASCII("MUA-MUAPACK-V2") || 0x00 || bytes(mua-pack.json)
keyId             = hex(SHA256(SPKI_DER(publicKey)))[0:24]

|| 表示字节连接；0x00 是一个 NUL 字节，不是两个文本字符。签名使用完整消息，不先将消息哈希再交给 Ed25519。可信公钥必须通过包外信任机制提供；同包公钥、keyId 或 OSS URL 本身不能建立生产信任。未知密钥／签名域／协议版本必须拒绝。

8.2 绑定链

受信公钥
  → signature.json → mua-pack.json 精确字节
    → 目标与基准清单摘要
    → 变化与载荷摘要
    → v1 环境清单 → 环境文件
    → v2 索引、远程文件哈希与地址、环境要求

ZIP 自身的 SHA-256 与大小由 OSS／数据库产物记录及分发 API 提供，不写入 ZIP 自身，避免循环引用。ZIP 摘要与包内签名作用不同，二者均须校验。v2 远程 URL、optional、环境及启动要求都被目标清单绑定；仅更换发布声明中的 URL 也必须新建发布，不能改旧签名。可信镜像传输只能获取同哈希内容。

公开 /manifest 接口的发布签名签署原始清单字节，不使用上述包签名域；不得将该 HTTP 签名当作 signature.json 的签名，反之亦然。构建签名不是上线证明：还需审核、修订锁、READY 产物及发布事务。

9. 分发 API

本节说明后端 REST 分发接口。普通包查询选择当前发布；固定发布刷新可读取当前绑定客户端的未归档历史发布。两者均要求服务器已上架、组织和客户端未归档、绑定有效。服务器展示时间只影响目录可见性，到期不会关闭下载。后台下载逐请求检查 DRAFT_READ／RELEASE_READ 与资源归属，始终返回完整包。

9.3 固定发布刷新与断点续传

GET /api/v1/servers/{serverId}/releases/{releaseId}/packages
    ?acceptedFormatVersions=2
    &baseReleaseId={installed-release-uuid}
    &baseManifestSha256={installed-manifest-sha256}
    &packageSha256={selected-zip-sha256}

GET {presigned-url}
Range: bytes=1048576-
If-Match: "{opaque-etag}"

启动器应保存并调用响应的 refreshUrl。该接口固定目标 releaseId，不随着最新版本切换；当前绑定客户端的未归档历史发布可刷新，草稿、跨客户端及下架资源不可访问。packageSha256 可选，但生成地址始终携带；若原更新不可提供而只能返回完整包，摘要不符返回 409，不能续传到其他字节。full.refreshUrl 另提供明确的完整包入口。JSON 响应不缓存。

下载地址由当前 OSS 适配器签发。MinIO、AWS S3 与通用 S3 使用 SigV4，阿里云 OSS、腾讯云 COS、华为云 OBS 使用各自签名机制。启动器必须将整个地址视为不透明的 GET URL。断点续传使用包含单个区间的 Range 请求，并在 ETag 可用时携带服务商返回的完整原值作为 If-Match；实际云端行为仍须按服务商验收。续传必须核对 206、Content-Range、总大小和 ETag；不能把 200 的完整响应直接追加。ETag 是不透明身份，不代替 SHA-256；错误 If-Match 返回 412。过期后刷新固定地址再续传，正在传输的请求无需因到期主动中断。GET 签名 URL 不可改用 HEAD，不可改写域名或查询。完成后验证整个 ZIP SHA-256、可信签名及全部载荷。启动器的实际下载／安装仍待接入。

HTTP含义

10. 安全与符合性校验

  1. 先限制 ZIP 条目数、压缩方式、展开大小与安全路径；识别 formatVersion 只用于选择校验器，不建立信任。
  2. 严格解码协议 JSON，检查已知字段、类型、身份、平台、文件冲突、资源上限与受保护路径。
  3. 从包外获取受信公钥，检查 keyId、元数据摘要和正确版本签名域。
  4. 核对目标／基准摘要及关系；从完整清单重算变化和载荷，要求与元数据完全一致。
  5. v1 核对所有目标环境引用及文件；v2 重新生成完整 mrpack 索引，并逐字节核对索引及摘要。
  6. 核对条目集合恰好等于协议文档与声明载荷，拒绝缺失／额外／重复文件；流式检查全部载荷大小、CRC 和 SHA-256。
  7. 校验完成后才进行安装、网络下载或命令授权；网络必须逐跳 HTTPS、校验公开地址并固定已核验 DNS 地址，代理不得绕过保护。校验远程实际大小和所有声明哈希后才进入缓存／启用目录。

整合包来源白名单当前由超管管理，默认关闭；停用白名单不会停用 HTTPS、SSRF、重定向、大小与哈希保护。v2 后台校验下载声明不证明远程字节已下载／验收，也不证明环境可启动。mrpack 不应被视作可直接信任的执行脚本。
