1. 引言与规范用语 / Introduction and requirement language

.muapack 是 MUA 管理平台面向 Minecraft Launcher 的签名客户端发布容器。每个包明确表示一个完整目标发布，或从一个明确基准发布到目标发布的更新。发布内容、客户端身份与服务器绑定相互独立。

.muapack is a signed client-release container produced by the MUA management platform for Minecraft launchers. A package represents either a complete target release or an update from one explicit base release to that target. Release content, client identity and server binding are separate concepts.

1.1 规范词汇 / Requirement vocabulary

必须（MUST）和不得（MUST NOT）表示符合协议的必要条件；应当（SHOULD）表示除非存在明确理由，否则应遵循的建议；可以（MAY）表示可选行为。协议字段、枚举和路径均区分大小写，除非明确说明。中英文描述表达同一规则，JSON 标识符不翻译。

MUST and MUST NOT express requirements for conformance. SHOULD expresses a recommendation that should be followed unless there is a specific reason not to. MAY expresses optional behavior. Fields, enumerations and paths are case-sensitive unless stated otherwise. Chinese and English describe the same rules; JSON identifiers are not translated.

实现边界：下文对 Launcher 的要求是安装器的实现契约，不表示当前 Launcher 已完成安装、增量恢复、optional 选择或真实游戏启动验收。

Implementation boundary: requirements for the Launcher below are an installer contract, not a claim that installation, delta recovery, optional selection or actual game-launch acceptance is already implemented.

3. 公共编码与容器 / Common encoding and container syntax

3.1 确定 JSON 编码 / Deterministic JSON encoding

  1. 协议 JSON 必须为 UTF-8，无 BOM、缩进、多余空白或结尾换行。

    Protocol JSON MUST be UTF-8, without a BOM, indentation, extra whitespace or a trailing newline.

  2. 对象键必须按 JavaScript 字符串比较的 UTF-16 代码单元顺序排序，包括数字形式的键；数组顺序保持不变。

    Object keys MUST be sorted by JavaScript string comparison of UTF-16 code units, including numeric-looking keys; array order is preserved.

  3. 字符串、整数、布尔与 null 采用 JSON.stringify 标量编码；对象以 :、, 连接，不加空白。不得含未配对代理项、非安全整数、重复键或未知契约字段。

    Strings, integers, booleans and null use JSON.stringify scalar encoding; objects use : and , without whitespace. Unpaired surrogates, unsafe integers, duplicate keys and unknown contract fields MUST NOT occur.

  4. 每份 JSON 最大 16 MiB，根节点深度为 0，递归深度不得超过 32。读取器必须用精确原始字节验证摘要与签名；不能格式化后再验签。

    Each JSON document is limited to 16 MiB. Root depth is 0 and recursive depth MUST NOT exceed 32. Readers MUST verify digests and signatures over exact original bytes, not reformatted JSON.

确定编码示例 / Deterministic encoding example:

{"a":[true,null],"b":2}

该示例的最后一个字节是 }，不是换行。此编码是 MUA 契约，不声称为其他 JSON canonicalization 标准。HTML 中便于阅读的缩进示例不是签名原始字节。

The last byte of this example is }, not a newline. This encoding is the MUA contract and does not claim conformance to another JSON canonicalization standard. Indented examples in this HTML are readable views, not the original signed bytes.

3.2 ZIP 与路径 / ZIP and paths

容器必须为 ZIP／ZIP64，仅使用 Store（0）或 Deflate（8）。不得使用加密、符号链接、显式目录条目、重复条目或未声明的附加文件。目录由文件路径隐含表示。必须核对解压大小、CRC-32 和内容摘要；CRC 不代替密码学摘要。

The container MUST be ZIP/ZIP64 using only Store (0) or Deflate (8). Encryption, symbolic links, explicit directory entries, duplicate entries and undeclared extra files are forbidden. File paths imply directories. Uncompressed size, CRC-32 and content digests MUST be checked; CRC does not replace cryptographic digests.

路径必须已是 NFC 相对路径，不以 / 开始，不含反斜杠、空段、. 或 ..。路径段不得含控制字符或 < > : " | ? *，不得以点／空格结尾，不得使用 CON、PRN、AUX、NUL、COM1–9、LPT1–9（包括扩展名形式）。清单必须拒绝大小写冲突与文件／目录冲突。所有实际写入还必须验证解析后的目标位于指定根目录内。

Paths MUST already be NFC relative paths, without a leading /, backslashes, empty segments, . or ... Segments MUST NOT contain control characters or < > : " | ? *, end in a dot or space, or use CON, PRN, AUX, NUL, COM1–9 or LPT1–9, including forms with extensions. Inventories MUST reject case collisions and file/directory conflicts. Actual writes MUST also confirm that the resolved destination remains within its designated root.

4. muapack v1

v1 是带完整预安装文件与精确运行环境的单平台容器。包内内容以 SHA-256 对象存储；安装位置由目标平台清单决定，不由对象 ZIP 路径决定。

v1 is a single-platform container of prepared files and exact runtimes. Content is stored as SHA-256 objects; the target platform manifest, not an object's ZIP path, determines its installation destination.

4.1 容器布局 / Container layout

client-1.4.3-windows-amd64.muapack

必须携带目标引用的全部环境清单，不要求携带旧基准的环境清单。每个载荷摘要仅对应一个对象条目；同字节文件可复用同一对象。未声明图标、许可证或变更说明不得作为额外 ZIP 文件添加；需要分发时，应纳入目标清单文件或已定义字段。

All environment manifests referenced by the target MUST be included; old base environment manifests are not required. Each payload digest maps to exactly one object entry, reusable by files with identical bytes. Undeclared icons, licenses or changelogs MUST NOT be added as extra ZIP files; distributed content must be represented by target files or defined fields.

5. muapack v2

v2 是基于 mrpack 的签名下载配方容器：MUA 保留本地 overrides 字节及完整发布／更新信息，Launcher 负责远程文件和运行环境。v2 不是 v1 的预安装包，也不是只含 URL 的空包；本地模组、配置和资源仍被保留。

v2 is a signed mrpack-based download-recipe container: MUA retains local override bytes and complete release/update information, while the Launcher obtains remote files and runtimes. v2 is neither a v1 prepared installation nor an empty URL-only package; local mods, configuration and resources remain included.

5.1 容器布局 / Container layout

client-1.4.3.muapack
├── mua-pack.json
├── modrinth.index.json
├── metadata/target-manifest.json
├── metadata/base-manifest.json             [update only / 仅更新包]
├── metadata/signature.json
└── overrides/<path>                       [local payload / 本地载荷]

当前输入支持标准 mrpack 与已验证的 PCL 内包封装。普通 .minecraft ZIP 不能通过猜测远程地址成为 v2。上传前显式选择分发格式；输入格式不决定输出版本。归一化按远程声明→overrides→client-overrides 叠加，本地覆盖同路径远程文件并继承 optional；server-overrides 与 client unsupported 文件不进入客户端。

Current inputs are standard mrpack and the verified PCL nested-package wrapper. A plain .minecraft ZIP cannot become v2 by guessing remote URLs. Distribution format is chosen explicitly before upload; input format does not determine output version. The ZIP's own SHA-256 and size live in OSS/database artifact records and distribution API responses, not inside the ZIP, avoiding a circular reference. Archive digests and internal signatures serve different purposes; both MUST be verified. v2 target manifests bind remote URLs, optional state, runtime and launch requirements. Even changing only a declared URL requires a new release, not editing an old signature. Trusted mirror transport may only retrieve matching hashed content.

公开 /manifest 接口的发布签名签署原始清单字节，不使用上述包签名域；不得将该 HTTP 签名当作 signature.json 的签名，反之亦然。构建签名不是上线证明：还需审核、修订锁、READY 产物及发布事务。

The public /manifest release signature signs raw manifest bytes without the package domain above. It MUST NOT be substituted for the signature.json signature, or vice versa. A build signature is not proof of publication: review, revision locking, READY artifacts and the publication transaction are also required.

9. 分发 API / Distribution API

此节描述当前后端 REST 分发契约，作为容器协议的传输配置。公开请求仅分发当前已上线、有效绑定、未归档的发布。管理下载另行检查 DRAFT_READ／RELEASE_READ 与资源归属，始终下载完整包。

This section describes the current backend REST distribution contract as a transport profile for the container protocol. Public requests distribute only the current live, validly bound, unarchived release. Management downloads separately check DRAFT_READ/RELEASE_READ and ownership, and always return full packages.

Discovery negotiates only the current release format; capability ordering never selects historical releases. A platform-free v2 update request requires the base to cover the target's declared platforms, preserving restricted legacy packages.

9.3 固定发布刷新与 S3 续传 / Pinned release renewal and S3 resumption

GET /api/v1/servers/{serverId}/releases/{releaseId}/packages
    ?acceptedFormatVersions=2
    &baseReleaseId={installed-release-uuid}
    &baseManifestSha256={installed-manifest-sha256}
    &packageSha256={selected-zip-sha256}

GET {presigned-url}
Range: bytes=1048576-
If-Match: "{opaque-etag}"

Launcher 应保存并调用响应的 refreshUrl。该接口固定目标 releaseId，不随着最新版本切换；当前绑定客户端的未归档历史发布可刷新，草稿、跨客户端及下架资源不可访问。packageSha256 可选，但生成地址始终携带；若原更新不可提供而只能返回完整包，摘要不符返回 409，不能续传到其他字节。full.refreshUrl 另提供明确的完整包入口。JSON 响应不缓存。

The Launcher SHOULD persist and request refreshUrl. Renewal pins the target releaseId rather than following new publications. Unarchived published history of the currently bound client is accessible; drafts, other clients and unlisted resources are not. packageSha256 is optional but always present in generated renewal URLs. If only full is available instead of the original update, a digest mismatch returns 409, preventing continuation with different bytes. full.refreshUrl explicitly selects full. JSON responses are not cached.

预签名 URL 使用 AWS SDK SigV4 GetObject，未绑定 Range，支持一个请求一个字节范围。续传必须核对 206、Content-Range、总大小和 ETag；不能把 200 的完整响应直接追加。ETag 是不透明身份，不代替 SHA-256；错误 If-Match 返回 412。过期后刷新固定地址再续传，正在传输的请求无需因到期主动中断。GET 签名 URL 不可改用 HEAD，不可改写域名或查询。完成后验证整个 ZIP SHA-256、可信签名及全部载荷。Launcher 的实际下载／安装仍待接入。

AWS SDK SigV4 GetObject URLs leave Range unsigned and support one byte range per request. Resumption MUST check 206, Content-Range, total size and ETag; a full 200 response MUST NOT be appended. ETag is opaque identity, not SHA-256; a failed If-Match returns 412. Renew the pinned link for a new request after expiry; an active transfer need not stop at expiry. A signed GET URL cannot be used as HEAD or rewritten. Finally verify the whole ZIP SHA-256, trusted signature and all payload. Actual Launcher download/installation remains pending.

10. 安全与符合性校验 / Security and conformance validation

  1. 先限制 ZIP 条目数、压缩方式、展开大小与安全路径；识别 formatVersion 只用于选择校验器，不建立信任。

    First constrain ZIP entry count, compression, uncompressed size and safe paths. Detecting formatVersion only selects a validator; it establishes no trust.

  2. 严格解码协议 JSON，检查已知字段、类型、身份、平台、文件冲突、资源上限与 protected 路径。

    Strictly decode protocol JSON; validate known fields, types, identity, platform, file conflicts, limits and protected paths.

  3. 从包外获取受信公钥，检查 keyId、元数据摘要和正确版本签名域。

    Obtain a trusted key externally and verify keyId, metadata digest and the correct version's signature domain.

  4. 核对目标／基准摘要及关系；从完整清单重算变化和载荷，要求与元数据完全一致。

    Check target/base digests and relationships; recompute changes and payload from complete inventories and require exact metadata agreement.

  5. v1 核对所有目标环境引用及文件；v2 重新生成完整 mrpack 索引，并逐字节核对索引及摘要。

    For v1, verify every target environment reference and file. For v2, regenerate the complete mrpack index and compare its bytes and digest.

  6. 核对条目集合恰好等于协议文档与声明载荷，拒绝缺失／额外／重复文件；流式检查全部载荷大小、CRC 和 SHA-256。

    Require the entry set to equal exactly the protocol documents and declared payload, rejecting missing/extra/duplicate files; stream-verify all payload sizes, CRCs and SHA-256 digests.

  7. 校验完成后才进行安装、网络下载或命令授权；网络必须逐跳 HTTPS、校验公开地址并固定已核验 DNS 地址，代理不得绕过保护。校验远程实际大小和所有声明哈希后才进入缓存／启用目录。

    Only after validation proceed to installation, network fetching or command consent. Network requests MUST enforce HTTPS at every hop, public-address checks and pinned validated DNS addresses; proxies MUST NOT bypass protection. Validate actual remote size and every declared hash before caching or activation.

整合包来源白名单当前由超管管理，默认关闭；关闭不关闭 HTTPS、SSRF、重定向、大小与哈希保护。v2 后台校验下载声明不证明远程字节已下载／验收，也不证明环境可启动。mrpack 不应被视作可直接信任的执行脚本。

The current super-admin-managed pack-source allowlist defaults to disabled. Disabled does not disable HTTPS, SSRF, redirect, size or hash protections. Backend v2 declaration validation is not proof that remote bytes were downloaded/accepted or that runtimes launch. mrpack must not be treated as a directly trusted execution script.
