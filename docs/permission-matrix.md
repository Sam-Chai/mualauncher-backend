# 最小权限矩阵提案

日期：2026-10-08。状态：组织模型下的设计提案，与[最小数据库模型](minimal-data-model.md)配套，尚未实现登录或授权代码。

用户已确定实施顺序：第一阶段应用层 RBAC，第二阶段 PostgreSQL RLS。当前阶段只更新设计，两层授权均未实现。第一阶段建议采用预置角色，不先开放自定义角色或直接按账号编辑任意权限集合。

## 1. 主体与权限范围

- **MUA 超级管理员**：启用的白名单账号且 `isSuperAdmin = true`，管理全部组织、服务器、客户端及账号。
- **组织管理员**：启用的白名单账号，目标组织中有启用的 `OrganizationMember` 且 `roles` 包含 `ORG_ADMIN`。可以管理该组织的资料、普通成员、全部已有服务器及专用客户端的基础业务，自动覆盖后续新增服务器。
- **普通组织成员**：只获得组织范围或指定服务器范围中明确授予的操作权限。加入组织本身不授予全部资源的管理权。
- **服务器管理员**：普通组织成员通过目标服的 `SERVER_ADMIN` 角色管理该服务器和它的专用客户端；该角色若按组织范围授予，则覆盖该组织所有服务器的基础业务。
- **MUA 审核员**：通过组织范围或单服范围权限获得审核能力，默认只读取和审核，不默认获得编辑、发布或版本切换权限。
- **只读人员**：获得相应读取权限的成员，不增加全局角色。
- **停用账号或成员**：账号停用影响所有组织；成员停用只影响对应组织，但同时使其组织角色和全部单服授权失效。
- **Launcher / 玩家**：使用对外服务器目录、当前 Manifest 和授权下载接口，不是面板管理主体；玩家认证规则仍待确定。

用户已确认保留 organization，并采用一服一客户端。NPU 组织管理员能管理 NPU RELEASE 与 NPU BETA；单服维护人员仍可以只管理测试服。同一组织的两个服务器也不能共用一条发布记录。

独立审核和归档制度继续有效。审核、签名发布、当前版本切换分别授权；组织管理员不因为可以管理全部子服务器而自动获得这些 MUA 发布流程权限。组织管理范围与全局服务器排序、颜色、上架等 MUA 权限分开。

## 2. 组织与全局操作矩阵

以下组织管理员的管理范围仅限本组织。其他角色若同时具有组织管理员身份，按该身份处理。

| 操作 | MUA 超管 | 组织管理员 | 普通成员 / 审核员 |
| --- | --- | --- | --- |
| 创建组织、分配组织内部 ID | 允许 | 不允许 | 不允许 |
| 修改组织别名、简介、头像 | 允许 | 允许 | 不允许 |
| 查看本组织成员管理列表 | 允许 | 允许 | 第一阶段不开放 |
| 将已在白名单中的账号添加为普通成员 | 允许 | 允许，仅本组织 | 不允许 |
| 停用、恢复普通成员 | 允许 | 允许，仅无管理员或 MUA 流程特权的普通成员 | 不允许 |
| 授予普通成员组织范围或单服基础权限 | 允许 | 允许，仅基础权限 | 不允许 |
| 授予、取消组织管理员身份 | 允许 | 不允许 | 不允许 |
| 授予审核、签名发布、版本切换权限 | 允许 | 不允许 | 不允许 |
| 创建、停用、恢复面板白名单账号 | 允许 | 不允许，不能通过组织成员入口创建全局账号 | 不允许 |
| 创建服务器、登记既有 MUA ID | 允许 | 第一阶段不开放 | 不允许 |
| 全局排序、颜色、上架控制 | 允许 | 不允许 | 不允许 |
| 归档、恢复组织、服务器或客户端容器 | 允许 | 第一阶段不开放 | 不允许 |
| 永久删除业务记录、账号或成员 | 不提供 | 不允许 | 不允许 |
| 分配超管身份或查看全局审计 | 允许，至少保留一个启用超管 | 不允许 | 不允许 |

组织管理员可以分配的基础角色限定为 `SERVER_ADMIN`、`CLIENT_EDITOR`、`SERVER_EDITOR`、`READ_ONLY`，其能力不超出基础操作权限。对拥有 `ORG_ADMIN`、`REVIEWER`、`PUBLISHER`、`RELEASE_OPERATOR` 的成员，角色、停用及授权调整由超管处理，不能通过撤销成员资格绕过上述边界。

组织成员管理和管理员身份的具体分配规则仍是本提案建议；组织管理员统一管理其子服务器是已确定需求。

## 3. 服务器与专用客户端操作矩阵

“组织管理员默认能力”覆盖该组织所有服务器；其他成员依赖明确的组织范围或目标服务器范围授权。超级管理员可以执行所有允许的业务动作，但也不能篡改旧发布内容。

| 操作 | 所需资源范围及权限 | 组织管理员默认能力 | MUA 审核员默认能力 |
| --- | --- | --- | --- |
| 查看服务器管理资料 | 目标服 `SERVER_READ` | 允许，全部本组织服务器 | 允许，获授权范围 |
| 修改服务器别名、简介、地址、图标 | `SERVER_EDIT` + `SERVER_READ` | 允许，全部本组织服务器 | 未默认授予 |
| 查看专用客户端草稿与识别结果 | `DRAFT_READ` + `SERVER_READ` | 允许 | 允许 |
| 上传整合包、创建新草稿 | `DRAFT_CREATE` + `SERVER_READ` | 允许 | 未默认授予 |
| 编辑草稿和补充识别信息 | `DRAFT_EDIT` + `DRAFT_READ` + `SERVER_READ` | 允许 | 未默认授予 |
| 复制为新草稿 | 源草稿需 `DRAFT_READ` / 源发布需 `RELEASE_READ`；目标需 `DRAFT_CREATE`，两侧均需 `SERVER_READ` | 本组织范围允许 | 未默认授予 |
| 提交或撤回审核 | `DRAFT_SUBMIT` + `DRAFT_READ` + `SERVER_READ` | 允许 | 未默认授予 |
| 归档、恢复未发布草稿 | `DRAFT_ARCHIVE` + `DRAFT_READ` + `SERVER_READ` | 允许 | 未默认授予 |
| 审核通过、驳回 | `DRAFT_REVIEW` + `DRAFT_READ` + `SERVER_READ` | 需超管另授 | 允许 |
| 签名并发布新版本 | `RELEASE_PUBLISH` + `DRAFT_READ` + `RELEASE_READ` + `SERVER_READ` | 需超管另授 | 需超管另授 |
| 查看客户端历史版本 | `RELEASE_READ` + `SERVER_READ` | 允许 | 允许 |
| 切换当前版本或撤下当前客户端 | `RELEASE_ACTIVATE` + `RELEASE_READ` + `SERVER_READ` | 需超管另授 | 需超管另授 |
| 编辑旧发布内容、改绑服务器或组织 | 不提供；需要新草稿、新版本 | 不允许 | 不允许 |
| 归档、恢复发布版本 | 第一阶段超管专属 | 不允许 | 不允许 |
| 查看管理审计记录 | 第一阶段超管专属 | 不开放 | 不开放 |
| 取得其他服务器的版本作为当前版本 | 不提供，包含同组织其他服务器 | 不允许 | 不允许 |

修改组织、服务器或客户端展示别名不会改变其稳定识别符。跨服复制草稿必须在目标服务器的专用客户端下生成新草稿并重新审核签名；原发布记录、批准和签名不能直接改绑或复用。

## 4. RBAC 角色、权限及作用域

预置角色的权限映射在后端统一维护，分配给用户的是带作用域的角色，操作权限由角色展开得出。`Account.isSuperAdmin` 代表最小模型中的全局 `SUPER_ADMIN`；`OrganizationMember.roles` 为组织范围角色；`ServerGrant.roles` 为单服务器角色。`ORG_ADMIN` 只允许组织范围，`SUPER_ADMIN` 只允许全局范围；其他角色可以按组织或单服务器授予。

组织资料及成员操作使用 `ORG_EDIT`、`ORG_MEMBERS_READ`、`ORG_MEMBERS_MANAGE`，由 `ORG_ADMIN` 展开得到，只对所属组织生效。普通组织成员没有这些能力。服务器/专用客户端操作权限如下，直接权限数组不再作为用户授权存储方式：

| 权限值 | 用途 | 依赖权限 |
| --- | --- | --- |
| `SERVER_READ` | 查看服务器管理资料 | 无 |
| `SERVER_EDIT` | 编辑服务器基础资料 | `SERVER_READ` |
| `DRAFT_READ` | 查看专用客户端草稿及解析结果 | `SERVER_READ` |
| `DRAFT_CREATE` | 上传并创建该客户端的新草稿 | `SERVER_READ` |
| `DRAFT_EDIT` | 修改候选内容 | `SERVER_READ`、`DRAFT_READ` |
| `DRAFT_SUBMIT` | 提交或撤回审核 | `SERVER_READ`、`DRAFT_READ` |
| `DRAFT_ARCHIVE` | 归档或恢复未发布草稿 | `SERVER_READ`、`DRAFT_READ` |
| `RELEASE_READ` | 查看专用客户端的发布历史 | `SERVER_READ` |
| `DRAFT_REVIEW` | 审核已提交候选版本 | `SERVER_READ`、`DRAFT_READ` |
| `RELEASE_PUBLISH` | 请求后端签名并发布已批准修订 | `SERVER_READ`、`DRAFT_READ`、`RELEASE_READ` |
| `RELEASE_ACTIVATE` | 切换所属服务器的历史发布或撤下当前引用 | `SERVER_READ`、`RELEASE_READ` |

有效权限是启用成员的组织范围角色与目标服务器角色展开后的权限并集。每个预置角色的映射必须包含其动作依赖，不在分配时悄悄扩大角色或作用域；后端检查有效集合，未知角色、未知权限和不合法作用域默认拒绝。每次请求仍验证账号、成员、资源归属和状态。

这些是追加角色授权，不提供隐式拒绝覆盖。撤销单服角色不能抵消组织范围角色；需要限制管理员只管理测试服时，先撤销 `ORG_ADMIN` 和其他覆盖全组织的相应角色，再授予测试服角色。任何普通成员授权都不能跨组织引用成员或服务器。

建议第一阶段的固定角色目录如下；角色组合仍受到业务状态限制：

- `SUPER_ADMIN`：全局 MUA 管理动作及全部资源权限；全局唯一作用域，不绕过发布不可变等规则。
- `ORG_ADMIN`：本组织八项基础服务器/客户端权限，以及组织资料、普通成员管理；不包含 MUA 审核、发布、切换权限。
- `SERVER_ADMIN`：`SERVER_READ`、`SERVER_EDIT`、`DRAFT_READ`、`DRAFT_CREATE`、`DRAFT_EDIT`、`DRAFT_SUBMIT`、`DRAFT_ARCHIVE`、`RELEASE_READ`。
- `CLIENT_EDITOR`：`SERVER_READ`、`DRAFT_READ`、`DRAFT_CREATE`、`DRAFT_EDIT`、`DRAFT_SUBMIT`、`DRAFT_ARCHIVE`、`RELEASE_READ`，不编辑服务器资料。
- `SERVER_EDITOR`：`SERVER_READ`、`SERVER_EDIT`。
- `REVIEWER`：`SERVER_READ`、`DRAFT_READ`、`RELEASE_READ`、`DRAFT_REVIEW`。
- `PUBLISHER`：`SERVER_READ`、`DRAFT_READ`、`RELEASE_READ`、`RELEASE_PUBLISH`。
- `RELEASE_OPERATOR`：`SERVER_READ`、`RELEASE_READ`、`RELEASE_ACTIVATE`。
- `READ_ONLY`：`SERVER_READ`、`DRAFT_READ`、`RELEASE_READ`。

一个用户可持有多个作用域角色。例如对 NPU 授予 `ORG_ADMIN` 会覆盖其正式服、测试服及新增服；只对测试服授予 `SERVER_ADMIN` 不会获得正式服权限；组织范围 `REVIEWER` 加单服 `PUBLISHER` 允许审核全组织，但只发布获授发布角色的服务器。

初期角色目录固定，普通管理页面不允许修改角色—权限映射。未来若需要自定义角色，再增加 Role/RolePermission 及角色分配结构，并保留作用域和不可自行提权的边界。

审核、发布、切换不互相隐含。发布权限仅允许调用后端签名服务并完成所属服务器首次发布绑定，不授予私钥访问权；切换权限不能创建新发布或绕过上架、归档限制。

## 5. 状态、归档与请求校验

账号和成员均须启用；启用的 MUA 超管无需组织成员记录，但也不能绕过资源状态和发布不可变限制。组织、服务器、客户端容器任何一层归档都会阻止对应业务写入和分发；历史读取和授权恢复操作另行检查。不因查询到一个启用草稿就忽略其上层资源状态。

草稿的 `DRAFT` / `REJECTED` 状态可编辑；`SUBMITTED` / `APPROVED` 内容锁定；撤回或修改使旧审核失效；`RELEASED` 源内容永久锁定。已发布内容、版本标签、服务器归属、Manifest 和签名对任何账号均不可修改。审核人与提交人是否必须不同仍待确定，目前提案不强制双人审核。

删除统一为归档：组织、服务器、客户端、未发布草稿和发布版本保留记录与历史；账号和成员采用停用，授权撤销清空角色并保留行。归档当前发布或客户端清空所属服务器当前引用；归档服务器还下架该服；归档组织关闭其全部子服务器的上架状态和当前引用。单服归档不影响同组织其他服务器。

归档不直接删除 OSS/CAS 对象，也不释放 server ID 或已发布版本标签。恢复不自动上架、设为当前版本或恢复被单独归档的子资源。所有归档与恢复记审计，面板不提供永久删除。

每个管理请求从数据库解析真实组织、服务器和客户端归属，检查账号、成员、有效权限和状态。不能相信请求自报的组织 ID、角色或 server ID。草稿/发布详情、原始包下载、搜索、分页和统计都限制资源范围；嵌套路径组织、服务器必须与资源归属一致。

更新接口按动作限制字段，不能整体写入请求体。组织管理员不能夹带超管标记、排序、颜色、上架、审核结论、签名或其他组织归属字段。原始上传沿用草稿读取权限；公开分发仅依据当前可用版本，不开放 bucket 列表或任意对象 key 下载。

发布、切换、归档和授权撤销在统一事务、锁顺序下重新检查权限与修订。停用账号、成员或撤销授权后，旧会话和在途 Worker 不得提交依据旧权限的新操作。Worker 只处理明确任务范围，不能自动获得审核或发布能力。

至少保留一个启用超管；并发停用或降级时在同一保护事务内校验。组织管理员的普通成员管理不能修改其自身管理员角色或通过停用特权成员取消 MUA 授权。

HTTP 错误建议：未认证 `401`，无操作权限 `403`，无权读取的管理资源按不存在处理。公开接口与管理接口分开，玩家下载不依赖面板白名单。

## 6. 第二阶段 PostgreSQL RLS

应用层 RBAC 继续负责角色对应的业务动作、字段限制及审核状态，RLS 在数据库中再检查查询或写入的行范围。第一阶段所有查询都要主动限定组织及服务器，不能以未来会有 RLS 为由省略范围过滤。

阶段二的策略应同时涵盖读取范围和新增/更新后的归属检查，不能只过滤 SELECT，也不能仅凭“属于某组织”放行该组织全部行而绕过单服角色。原始上传、OSS/CAS 对象下载不经过 PostgreSQL 行策略，继续执行服务端授权。

运行连接使用非 PostgreSQL 超级用户、无 `BYPASSRLS` 且与迁移/表所有者分离的数据库账号，必要时明确使用 `FORCE ROW LEVEL SECURITY`。应用层 `SUPER_ADMIN` 由策略表达相应访问范围，不通过赋予数据库超级用户实现。数据库表权限和行策略分别配置，不把 RLS 当成全部授权。

服务端从已认证会话设置账号与组织/服务器访问上下文，在同一个事务内执行相关查询，使用事务局部设置避免连接池复用带入旧身份。缺失或无效身份默认拒绝管理数据，公开分发和 Worker 采用明确的独立策略。事务上下文是数据库策略的输入，不是前端可以自行指定的管理员标记，也不替代用户认证。

RLS 不保护字段级修改或整个发布业务流程，现有字段白名单、不可变快照保护、审计、归档及并发控制继续保留。政策设计还需处理成员/角色查询、后台任务及策略递归等问题，并以实际运行账号验证。实现细节参考 [PostgreSQL RLS](https://www.postgresql.org/docs/current/ddl-rowsecurity.html) 和 [事务局部 SET](https://www.postgresql.org/docs/current/sql-set.html)。当前没有启用 RLS。

## 7. 实现后的验收场景

1. 建立 NPU、另一个高校两个组织；NPU 下有 NPU RELEASE、NPU BETA，各有一个客户端容器。
2. NPU 管理员可以管理正式服、测试服及新增服务器的基础资料与草稿，不需重复逐服授权；不能操作另一个高校。
3. 普通 NPU 成员只获测试服授权时，不能读取正式服管理草稿、编辑正式服或请求其原始包。
4. 即使两服属于 NPU，正式服也不能引用测试服的发布 ID；同样文件可复用 CAS 对象，但发布记录独立。
5. 草稿复制到另一服务器需源读取、目标创建授权，生成新草稿并重新审核；原版本不能改绑。
6. 单服审核员不能审核未获授权的另一服；组织范围审核员可审核该组织全部及新增服务器，但不能发布或编辑内容，除非另行授权。
7. 发布须绑定被批准的修订和摘要；发布、切换、排序与颜色权限不能互相替代。
8. 停用组织成员使其组织角色及全部单服角色失效；清空单服角色不抵消仍有效的组织范围角色。
9. 组织管理员不能建立新白名单账号、提升管理员、授予审核/发布特权或修改其他组织的授权。
10. 旧发布不能修改，归档不物理删除记录或对象；归档单服不影响其他服，归档组织关闭全部子服分发，恢复后需要显式上架或切换。
11. Launcher 只安装所属服务器唯一当前、已签名且所有上层资源未归档的发布，不访问草稿或面板管理信息。
12. 最后一个启用超管的并发停用或降级不能绕过保护。
13. 第一阶段检查所有角色组合及作用域，确保单服角色不能被当作全组织角色，组织管理员不能授予 MUA 特权角色或编辑权限映射。
14. 第二阶段使用实际运行账号验证 RLS：即使遗漏组织/服务器过滤，越界行仍不可读写；缺失上下文拒绝管理访问；连接池复用、事务回滚及后台任务不会串用身份。数据库所有者或超级用户的测试成功不能作为 RLS 生效证据。
