# muapack v1 发布前组包设计

更新时间：2026-10-09。协议模型、差异生成、签名及只读 ZIP 校验器已实现，见 [muapack v1 协议](muapack-v1.md)。后台任务、环境缓存、UI 和发布门槛已接入，具体范围和限制见[实施说明](muapack-worker.md)。下文保留设计背景；与实施说明有差异时以后者为准。

## 最新需求

- 分发统一使用 `.muapack`，区分整包与更新包。更新包记录所有变化文件，服务端继续通过 CAS 去重和组包。
- 采用发布前预生成，取代此前讨论的 Launcher 下载时现场组包作为主要路径。
- 发布页面提供目标平台多选，默认全选：Windows amd64、Windows aarch64、Linux amd64、Linux aarch64、macOS amd64、macOS aarch64。
- Worker 持续后台生成所选平台的包并保存到 OSS；关闭页面、退出浏览器不取消任务。
- 所有必需产物未准备完成时，不允许发布。后台 API 也执行此检查，不能只禁用前端按钮。
- 客户端管理表格显示真实组包进度，展开可查看各平台状态、错误和重试。
- 游戏、加载器和 Java 由 Worker 准备并保存到独立环境 bucket，相同环境校验后复用。
- `mua-pack.json` 记录客户端信息、环境引用、启动描述及文件清单。游戏参数、JVM 参数、内存管理和启动前操作属于协议设计范围。

## 建议的准备流程

1. 上传源包，Worker 识别，前端提前回填客户端信息，然后完成远程文件下载（如适用）、校验和 CAS。
2. 管理员确认版本资料和目标平台，保存一个固定的候选内容修订。
3. 持久化各平台构建任务，Worker 准备环境、构建整包和所需更新包，验证后保存至 OSS。前端只轮询任务状态，不承担任务生命周期。
4. 审核对应候选内容修订；构建和审核是否并行属于实施选择。最终可分发产物必须完成签名验证要求。
5. 发布事务检查权限、审核修订、构建修订、必需产物状态和现有版本／绑定修订，全部满足才创建公开发布或启用当前版本。

“源包解析完成”与“可发布产物准备完成”是不同状态。不能让现在的 ClientUpload READY 同时承担两种含义；导入表单应能在组包尚未完成时展示识别结果。

内容修订和生成的启动描述当前不可原地编辑；需要上传新版本。平台选择可以调整，已通过的审核会失效，必须重新审核，已完成的同平台内容可复用。迟到的旧任务不能将新修订标记为完成。已发布记录和产物保持不可变。

## 平台和环境

协议采用六个有限平台枚举，显示名称与内部值分离；amd64／aarch64 别名归一化已在协议模型中实现。

按平台选择 Java、Minecraft 原生库及受平台条件控制的其他依赖。缓存身份覆盖精确 Minecraft 版本、加载器版本、Java 发行商和完整构建号、平台、环境清单摘要，以及影响输出的环境解析规则版本。

默认全选不代表所有 Minecraft／加载器组合已支持这六个平台。缺少原生库、兼容 Java 或所需构建能力时，平台任务应明确失败并阻止发布，不能静默取消勾选或标记成功。管理员可明确调整平台选择并重新准备、审核对应修订。

Windows Worker 可以下载其他平台文件；需要执行目标平台安装器／原生处理步骤的适配器，可能需要对应平台 Worker。完成文件校验不等于完成六个平台的真实游戏启动验证。

环境任务合并相同缓存身份的并发请求；仅完整校验且可用的环境允许被引用。环境引用独立追踪，不能随单个客户端删除而清除仍被其他发布使用的文件。

## 整包和更新包

- 整包携带目标平台所需的完整内容。
- 更新包固定基准发布和目标候选发布及其清单摘要，包含目标完整清单、变化清单和变化所需的文件内容。
- 变化包括新增、修改、移除、策略变化，以及环境和启动配置变化；文件记录包含目标路径、策略、大小及相关旧／新 SHA-256。
- 相同字节在包内可复用；增量单位为完整文件。
- `preserve` 存在时不覆盖、不自动删除；旧 `managed` 文件的清理和备份行为仍需冻结，不能仅凭删除统计实施清理。
- Launcher 不能仅凭显示版本号应用更新包，必须检查发布身份、平台和基准状态；缺失或损坏的未变化文件需要修复策略。

建议每次更新预生成“上一当前发布 → 新候选发布”的更新包及新版本整包；首次发布只需整包。是否额外预生成更早基准的更新包、非匹配基准回退整包的规则仍待确认，不能默认生成全部历史两两组合。

发布门槛检查固定的必需产物集合：每个所选平台的整包，以及本次指定基准所要求的更新包。上一当前发布未提供某个平台时，该平台是否仅要求整包需在协议中明确。

## 后台任务、进度和发布门槛

建议平台构建状态：等待、准备环境、组装、上传 OSS、校验、完成、失败；状态名称不是已实现 API 契约。

表格示例：`组包中 · 平台完成 3/6`；展开显示各平台、整包／更新包、当前阶段、文件／字节进度、包大小、错误及重试。下载、压缩和上传的进度分别记录；总进度按明确定义的工作量计算，不用定时器模拟百分比。

Worker 使用持久任务、租约和心跳，进程重启后可恢复，失败的平台可重试，完成的产物可复用。不得覆盖不同内容修订的对象。构建失败保留现有已发布客户端，不自动切换服务器绑定。

发布事务必须确认全部必需产物是对应候选修订的 READY 产物，且具备大小、摘要、确定的 OSS 对象身份和签名验证依据。失败、处理中、旧修订、缺失产物均不能发布；直接调用标准 API 同样受限。

## OSS、CDN 和签名

组包后保存为不可变 OSS 对象，下载采用固定的发布／平台／产物摘要身份，CDN 可以复用缓存。个人账号、登录令牌、本机路径和具体内存分配不写入共享包；Launcher 在启动时填入。

草稿包和环境 bucket 保持私有，不因构建完成自动开放下载。公开下载仍检查当前发布和资源状态，CDN 鉴权、短期授权与撤回行为需联合设计。

签名必须覆盖客户端内容、平台环境引用和启动配置；更新包还要绑定基准、目标及变化清单。现有签名清单保留原字节，不能改写后沿用旧签名。

当前实现是在 publish 动作内生成 Release 签名。新流程需要明确发布前签名／封装步骤，保证发布门槛验证的是最终可分发产物，而不是发布后仍需修改的 ZIP。最终签名封装、候选发布 ID 分配及精确字节规则待协议冻结；不得形成包内摘要／签名的循环引用。

## 下一步

协议第一阶段已经建立模型、签名和 ZIP 校验能力。下一步设计持久构建模型和 API，接入 Worker 环境准备、生产组包、发布门槛及表格进度，最后联调 Launcher。更新基准先采用上一当前发布，清理策略由包显式记录，Launcher 执行细节需联调。网页和自动化继续共用 ClientDraft／ClientRelease，不增加第二套发布系统。
